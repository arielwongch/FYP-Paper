Welcome. This update focuses on the literature review and research question refinement completed over the past two weeks. The project aims to build an LLM agent framework with interchangeable memory modules, then compare their task quality and system overhead on long-horizon tasks.

I have reviewed the core mechanisms and evaluation approaches in the survey, MemGPT, Mem0, and A-MEM, with ReAct as background for the agent loop. Today I will cover three things: what is complete, what common structure emerged from the papers, and how that understanding becomes a runnable baseline over the next two weeks.

This is not a final design review. It is the transition from reading to implementation, ending with the concrete deliverables for the next meeting.

01 · completed since last meeting

Four papers read, four design perspectives

Memory in the Age of AI Agents · Survey

A lifecycle view: memory formation, evolution, and retrieval, plus a map of benchmarks and open problems.

MemGPT · virtual context management

Treats memory as context management: working context is separated from a larger external archive.

Mem0 · production-oriented memory

Extracts candidate facts and chooses ADD, UPDATE, DELETE, or NOOP when new information arrives.

A-MEM · agentic memory

Uses atomic notes, links, and memory evolution to build a connected knowledge structure.

The main completed task since the last meeting was a focused reading pass over four papers in the paper folder. I started with the survey to understand the vocabulary and the overall research landscape, then read MemGPT, Mem0, and A-MEM as three different system perspectives.

The survey gave me the lifecycle view. MemGPT showed how memory can be treated as virtual context management. Mem0 made the write and update decisions explicit through ADD, UPDATE, DELETE, and NOOP. A-MEM showed how atomic notes and links can support a continuously evolving memory structure.

These are not four interchangeable implementations. They make different design choices, which gives us a useful basis for deciding what the baseline framework should expose.

02 · lessons from the reading

What I learned: memory is a policy, not just storage

01 · Selective formation

A system must decide what is worth keeping from messages, tool outputs, or feedback.

02 · Explicit evolution

Memory must handle duplicates, conflicts, stale facts, and updates instead of only appending.

03 · Task-aware retrieval

The useful memory depends on the current task, observation, query, and context budget.

The most important lesson is that memory is a policy, not just storage. The system decides what to write, how to change an existing memory, and what to retrieve for the next action. A vector database can be one backend, but it is not the whole memory architecture.

The papers also suggest that quality depends on the full lifecycle. Retrieval alone cannot fix poor formation, and formation alone cannot resolve contradictions or identify which memory is relevant to the current task.

This is the reason the planned framework needs a common write, retrieve, and update interface. It lets the experiment compare these policy choices directly rather than comparing unrelated agent implementations.

03 · proposed framework contract

One agent loop, replaceable memory policy

Runtime flow

# each interaction step observation → retrieve(query, state) context = recent + retrieved action = agent(context, tools) write(observation, action, outcome) update(memory_state)

Shared module interface

class MemoryModule: write(event) → candidates retrieve(query, k) → items update(candidates) → state stats() → cost, size, latency

The experiment changes the memory module, not the agent loop, task input, or evaluator.

This is the proposed technical contract for the framework. The agent loop receives an observation, asks the selected memory module for relevant context, combines that with the recent window, and then produces an action or tool call.

After the step, the same module receives the event, action, and outcome. It can decide whether to write a candidate, update existing state, or do nothing. The important point is that the loop does not know whether the backend is a summary, vector index, or fact graph.

The shared interface exposes write, retrieve, update, and stats. Stats are part of the contract because this project evaluates system behaviour as well as answer quality. For a fair comparison, the task input, backbone, prompt budget, and evaluator stay fixed while the memory policy changes.

03 · implementation target

First, establish four interchangeable baselines

1
Sliding window

Use recent messages as the simplest context-budget baseline.

2
Summary memory

Compress history and measure the trade-off between recall and latency.

3
Retrieval memory

Retrieve relevant passages with embedding similarity and measure overhead and noise.

4
Structured fact memory

Maintain entities, relationships, and updates explicitly, following graph-style ideas from Mem0g.

The next step is not to pursue a complex adaptive memory immediately. I will first run four interchangeable modules, keeping the memory policy as the main changing factor while holding the agent backbone, task inputs, and evaluator as consistent as possible.

Sliding window is the control group; summary memory tests compression; retrieval memory tests external storage and similarity search; structured fact memory tests explicit facts and relationships. Together, they represent the main design choices that appeared repeatedly in the reading.

Each module will implement the same write, retrieve, and update interfaces, while recording token usage, time, and storage. The later adaptive policy can then be based on observed baseline weaknesses rather than intuition.

05 · evaluation protocol

Measure memory as both quality and systems behaviour

Task quality

Q1
Recall

Can the agent recover facts from earlier sessions?

Q2
Consistency

Does the answer remain aligned with stored facts?

Q3
Knowledge update

Can new information override or extend old memory?

Q4
Task success

Does memory improve completion of the multi-session task?

System behaviour

S1
Latency

End-to-end time and memory operation time per step.

S2
Retrieval overhead

Extra calls, tokens, and ranking work introduced by memory.

S3
Storage growth

Memory size and redundancy as history length increases.

S4
Scalability

How costs change across longer histories and sessions.

The evaluation needs two axes. On the quality side, the project brief calls for recall, consistency, knowledge updating, and task success. These separate remembering a fact from using it correctly, and separate retrieving old knowledge from handling a changed fact.

On the systems side, I will record latency, retrieval overhead, storage growth, and scalability as histories become longer. This matters because a memory module that improves F1 but adds large prompt or retrieval costs may not be a useful system design.

The first implementation will use a single controlled task and a small Qwen backbone, then expand to a larger benchmark once the pipeline is stable. Each result should report the task configuration, model, memory module, and cost statistics so that comparisons remain reproducible.

To summarize the delivery criteria for the next meeting: first, a runnable modular framework with clear write, retrieve, and update interfaces. Second, four baselines that can be reproduced on the same task and backbone. Third, a first results table covering both quality and systems metrics.

I will deliberately leave the adaptive strategy until after the baselines. We do not yet know whether the main bottleneck is write selection, conflict resolution, retrieval noise, or storage growth. Measuring those failures first gives the adaptive policy a real basis.

The main conclusion today is that the literature review has moved the problem from “memory matters” to “memory lifecycle plus comparable interfaces.” Over the next two weeks, the code will test that abstraction. Feedback is especially welcome on whether the task and metrics can distinguish the four memory types, and which baseline should be prioritized first.
