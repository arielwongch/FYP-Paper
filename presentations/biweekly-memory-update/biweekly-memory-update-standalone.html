The main completed task was a focused reading pass over four papers. The survey gave me the lifecycle vocabulary. MemGPT showed virtual context management. Mem0 made write and update decisions explicit. A-MEM showed how atomic notes and links can support an evolving memory structure.

These are not interchangeable implementations. They make different design choices, which gives us a useful basis for deciding what the baseline framework should expose.

02 · lessons from the reading

What I learned: memory is a policy, not just storage

01 · Selective formation

A system must decide what is worth keeping from messages, tool outputs, or feedback.

02 · Explicit evolution

Memory must handle duplicates, conflicts, stale facts, and updates instead of only appending.

03 · Task-aware retrieval

Useful memory depends on the current task, observation, query, and context budget.

The lifecycle is the common comparison language across the papers.

#formation #evolution #retrieval3 / 8

The most important lesson is that memory is a policy, not just storage. The system decides what to write, how to change an existing memory, and what to retrieve for the next action.

Retrieval alone cannot fix poor formation, and formation alone cannot resolve contradictions or identify which memory is relevant to the current task. This is why the framework needs a common write, retrieve, and update interface.

03 · proposed framework contract

One agent loop, replaceable memory policy

Runtime flow

# each interaction step observation → retrieve(query, state) context = recent + retrieved action = agent(context, tools) write(observation, action, outcome) update(memory_state)

Shared module interface

class MemoryModule: write(event) → candidates retrieve(query, k) → items update(candidates) → state stats() → cost, size, latency

The experiment changes the memory module, not the agent loop, task input, or evaluator.

#architecture #interfaces #controlled-comparison4 / 8

This is the proposed technical contract. The agent receives an observation, asks the selected memory module for relevant context, combines it with the recent window, and produces an action or tool call.

After the step, the module receives the event, action, and outcome. It can write a candidate, update existing state, or do nothing. The loop does not need to know whether the backend is a summary, vector index, or fact graph.

#baselines #memory-modules5 / 8

I will first run four interchangeable modules, keeping the memory policy as the main changing factor while holding the agent backbone, task inputs, and evaluator as consistent as possible.

Sliding window is the control group; summary memory tests compression; retrieval memory tests external storage and similarity search; structured fact memory tests explicit facts and relationships. Each module will implement the same interfaces and record token usage, time, and storage.

#evaluation #quality #systems6 / 8

The evaluation needs two axes. On the quality side: recall, consistency, knowledge updating, and task success. These separate remembering a fact from using it correctly, and separate retrieving old knowledge from handling a changed fact.

On the systems side: latency, retrieval overhead, storage growth, and scalability as histories become longer. A memory module that improves answer quality but adds large prompt or retrieval costs may not be a useful system design.
